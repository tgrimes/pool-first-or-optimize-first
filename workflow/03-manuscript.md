# Stage 3: manuscript

## Purpose

Take a passed pilot and produce the manuscript: a first draft in draft mode on quick-run numbers, then revision rounds on the person's comments until the draft is settled. The repository is the research compendium, so every number is read from `results/` at render time, every claim rests on a Zotero item with its passage recorded, and the draft carries its markers until a person closes them.

## Inputs

- `project-spec.md`, `proposal.md`, and `pilot/` (the pre-registration, the results, `decisions.md`, the report).
- `manuscript/`: the skeleton `manuscript.qmd`, `manuscript-helpers.R`, `check-manuscript.py`, `build-bib.py`, `parts/`, `references.bib` (the seed), `citations.csv` (started at stage 1), `journals.csv`.
- `workflow/journals/`: the journal guide.
- `03-manuscript-brief.md`: the brief given to a worker that runs the steps.

## Preconditions

- `STATUS.md` says `piloted-pass`, and the spec's `[TO CONFIRM]` markers are resolved or will be carried into the draft as markers.
- A target journal and a fallback are chosen with the journal guide's worksheet and recorded in the spec's section 6.
- `renv::restore()` and `uv sync` have been run; R, Quarto, and uv are installed.
- Zotero is open with the Zotero MCP Plugin serving (`curl http://127.0.0.1:23120/ping` answers `pong`) and the local API on (`curl http://127.0.0.1:23119/api/users/0/items?limit=1` answers); the plugin's write operations are enabled if the Zotero collection is wanted. If either server is down, stop and say so before anything else.
- The stage's log is `manuscript/drafting-log.md` (the draft's banner reads its first line); process feedback goes at its end.

## The steps

Each step ends in a file someone can open. **Stop** marks a point where the step halts for a person's answer.

**0. Paper test.** Seven answers, one per step of the critique template, each qualified by method and setting and each pointing at the file where it is met: a procedure in wide use; a setting it was not built for; the estimand as a functional; the target and the bias term; a simulation that confirms it; a correction or a diagnostic; a confirmed dataset with a "what to show" claim. They go in `manuscript/drafting-log.md` under "Paper test" once step 1 has created the log, and the log's opening paragraph states their status in one line, which the draft's banner repeats. A "no" on the estimand, the formula, or the fix is stated at the top of the draft, not written around.

**1. Promote the pilot.** The pilot's functions are already in `R/` with tests, so there is nothing to port. Promote the pilot's script to `analysis/01_simulation.R` with a parameter block (factor levels, replicate count, cores), a seed per cell from the design table, paths through `here::here()`, PSOCK workers with the BLAS pinned to one thread in each, per-replicate output, the design table, `sessionInfo()`, and `results/run_info.rds`, which the simulation script owns; every other script writes `results/<name>_run_info.rds` (see Provenance). The design itself is written at the design stop below; until then the script carries the pilot's design. A per-replicate file above about 50 MB is git-ignored and the per-cell summaries the script computes from it are committed. `analysis/00_download.R` fetches what `data/raw/` lacks; if it cannot be run in the session, the README says so and the log carries a marker. Known-answer checks and code-identity checks are `tests/testthat/` tests covering every code path the production design uses, with the closed forms as expected values where they exist; plot code becomes figure functions in `R/` that the manuscript's chunks call, so the report, the slides, and the poster can draw the same figures. `devtools::document()`, `devtools::test()`, and `devtools::check()` run clean. Acceptance test: copy the pilot's saved summaries from `pilot/results/` into `tests/testthat/fixtures/` and write a testthat test, gated by an environment variable so that `R CMD check` stays fast, that runs the pilot's grid and seeds through the package's functions and compares every per-cell summary to floating-point precision; record the result in the log, and stop on a mismatch. A method whose only implementation is in Python is run through the uv environment as `CLAUDE.md` says (a package with `uv add 'name==version'`, scripts vendored into `inst/python/vendor/`, glue in `inst/python/<package>/` with pytest tests, an R wrapper in `R/`); when the environment cannot be built in the session, the method is drafted as planned with markers and its chunks left empty, and the decision is logged.

**2. References. Stop, up to twice.** Zotero is the only source of entries. (a) *Inventory:* every source the draft will cite, from the parent manuscript's bibliography, the pilot's opened sources (D0, or the report's citations), the spec's reading list, and the seed, each with the claim and section that need it. If the step was run before, the log points at the existing inventory and checklist rather than copying them. (b) *Availability:* look each candidate up by DOI and then by title. Available means the item is there, the record is complete enough to cite, and a PDF with full text is attached; a pre-1980 record or a book counts without a PDF. Report either an all-clear with the count, or a missing list grouped by what the person must do (add the item, attach the PDF, complete the metadata, correct a field), with every record fault found (missing DOI, lowercased journal, title typo, author list cut at ten, a date in the pages field) stated with the item, the field, and the value to enter. Stop until the library is updated. (c) *Build:* `python3 -I manuscript/build-bib.py manuscript/citations.csv manuscript/references.bib` exports each item from Zotero's local API, drops abstracts, file paths, access dates, keywords, and an article's publisher, remaps keys through the checklist, changes nothing else, and writes any remaining faults to `manuscript/zotero-fixes.md`. The checklist `manuscript/citations.csv` has one row per candidate: `key, zotero_item, grade, section, why, origin, identifier, identifier_source, pdf, usable, deviations_from_record, support_passage, read_date, verified_by, verified_date`. Create a Zotero collection named for the project and add every usable item; it is the only write made to the library, and it needs the plugin's write operations enabled.

**3. Draft, in six parts.**
1. *Purpose draft of the Introduction* and the list of claims (the spec's aims, as questions). Three paragraphs: the procedure and what it is meant to estimate; what it estimates under the realistic condition, in words and then as a formula; what the paper does. No exemplar manuscript; the guidance is the skeleton, the critique template's first three steps, and the how-to-write rules below.
2. *Design proposal.* **Stop.** A table of factors, levels, and the reason for each; the application plan (dataset, comparison, what to show); every element tied to the question it answers; every varied factor spanning a gradient from too small to matter to large, with the application placing the real data on it; the test the application uses (the spec's if it names one, otherwise the simulation's, marked); one cell of each method timed at the largest sample size as well as a typical one, so the proposal carries a runtime bound (the first SS1 run's estimate from a typical cell fell short by half); the performance measures named by target (bias against the formula, empirical SE or MSE, coverage where intervals are reported; type I error and power). Power is planned by default, not on request: for every method whose type I error is controlled (as a working rule, a rejection rate under about 10% for a test at 5%), cells with a true difference whose levels run from low power to about 80%, the levels informed by the real data and checked with a few low-replicate cells before the full run, and the real data placed on that gradient as on the others; a method with very poor type I error control is left out of the power cells, and the proposal says so. On approval, write `protocol.md` once from the approved design.
3. *Quick run.* The full design at a replicate count set by runtime (the grid finishes well within an hour), the production code with only the replicate count reduced, the application too if its code exists. `run_info.rds` says `run = "quick"`.
4. *Methods, the design section, Results, Discussion*, in that order, on the quick-run numbers, with the supplement skeleton holding the proofs. Design levels in the prose go through `lvl()`, results through `prov()`, and a range with its Monte Carlo error through `range_mcse()`, so no digit is typed. When a result contradicts a claim in the spec, the Results state the fact, the Discussion interprets it with a guard, and a `[TO CONFIRM]` quotes the spec's sentence. An exploratory probe that explains a result enters the paper only through a script that writes its numbers to `results/`; otherwise it stays in the log, and the interpretation it supports carries a marker. The journal's CSL file is copied beside the qmd and named in the YAML from the start; the profile's placement of the AI-use statement and its required back-matter headings override the skeleton's.
5. *Introduction revised* against the Results and Discussion; then the Abstract in the journal's headings.
6. *Second Zotero batch.* **Stop** if any source found while drafting is missing.

When the stops are switched off for a run, the worker decides at each one, records the decision and its reason in the log under "Decisions made in place of a stop", and marks in the draft what a person should look at. When a stop has been answered by a ruling, the worker applies the ruling; if the ruling's stated reason turns out to be wrong, the worker keeps the ruling, says so in the protocol with a dated note, and marks it in the draft.

**4. Revise for clarity, at least once.** Render the draft and read the rendered page from the title to the end of the Discussion as the journal's reader would, not as its author: someone who knows the field but has not read the spec, the protocol, or the log. Two passes over the text, two cross-checks, then a render. (a) *Paragraphs.* For each paragraph, write in the log the one question it answers for that reader; if its first sentence does not state the answer, rewrite the first sentence. Within the paragraph, why comes before what, and nothing is named (a method, a symbol, a study label) that the reader has not met without a phrase saying what it is. (b) *Sentences*, for the Abstract and the Introduction in full, the first paragraph of every other section, and every caption: each sentence has a subject and a verb the reader can find, states one fact or one reason, and can be paraphrased by the reader; a clause the reader would stumble on is replaced by what it meant; a sentence that needs the next one to make sense is joined to it or recast; a sentence that packs several ideas and terms together is split into the simple sentences it was built from, in the order a reader can follow (time against burden: one sentence for a simple topic, up to three for a complex one); a claim without a source is given one or removed; the sentence keeps the paragraph's subject rather than introducing another to carry a fact about it ("these methods were developed to", not "their authors' aim was to"). (c) *Cross-checks.* Each claim in the Abstract carries a number with its uncertainty, and the same number appears in Results; the Introduction's questions are answered in the Discussion in the same order and the same words; every label a caption uses is defined in the caption or in the text before the display. Settled points, from the first pass on SS1: an opening the person has accepted is exempt from (a); where answer-first and why-first collide, the first sentence states the answer with its reason in the "why, so what" form of the section "The fix" when the reason is short, and otherwise the answer first and the reason in the next sentence; "section" means every heading level, and the standard parts from `parts/` are exempt; a caption's numbers are computed like the prose's (build the caption in the setup chunk and pass it with `!expr`); a claim in the Abstract is a finding of the simulation or the application, not prior work or a recommendation; the Abstract and Results quote the same digits from the same expression; a name every reader in the field knows (limma, the Welch test) needs no phrase; a paragraph may be split or sentences moved within a section, with the split logged; the log lists the changes by section, quoting the rendered page, with one reason per block of like changes rather than per sentence. Record what changed and why in the log under "Revision pass", render again, and run the checker. Make a second pass when the first changed more than three sentences in any section, and apply the same rule to the second; the third pass, when due, is the person's. The pass lengthens a draft (the first on SS1 added about a tenth to the word count by splitting sentences), so the second pass also cuts what the splitting left redundant. The pass may be a person's or the worker's; at a handoff, the person makes the next one.

**5. Render and check.** `quarto render manuscript/manuscript.qmd` in draft mode (the default), then `python3 -I manuscript/check-manuscript.py manuscript/manuscript.qmd manuscript/manuscript.html --citations manuscript/citations.csv --bib manuscript/references.bib --journals journals.csv --journal <slug>`. Fix every error; answer every warning in the log as fixed or kept with a reason. The checker's word count splits a decimal and a possessive into two words, so it runs a few percent above a plain count; at a journal's limit, trust it rather than the plain count. Finish `drafting-log.md`. Clone the compendium to a scratch directory, run `renv::restore()` and `uv sync`, then the tests in both languages and `devtools::check()`, rerun the quick run, confirm the summaries match, and render. Delete `data/raw/` in the clone first so that `analysis/00_download.R` runs; compare downloaded files by checksum and files the script builds by content. Hand over the draft HTML, the qmd, and the log with the paper-test status, the open markers, the Zotero fixes, and the gap table.

**Final mode**, later, when production numbers exist: render with `-P draft:false`. The banner and gap table disappear, `prov()` refuses anything not labeled production, and the checker in `--final` errors on any marker.

## What each section must contain

**Abstract.** The headings and word limit of the target journal's profile. Every claim carries a numeric result with its uncertainty, through `prov()`: an estimate with its confidence interval or Monte Carlo standard error, a rate with its band, a count against its permutation or null count. In the first draft these are quick-run numbers; the final draft replaces them with production numbers in the same sentences.

**Introduction.** Three paragraphs. Paragraph 1 opens with why: the scientific question the procedure serves and what a user hopes to learn from it, before any method is named, because the reader's first question is why this matters, and a paragraph that jumps to describing methods leaves it unanswered. The opening balances the reader's time against the reader's burden: a simple topic takes one sentence, a complex one up to three simple sentences that build on each other, never one sentence that packs the three together (quick to read, hard to follow) and never a page of preamble (easy to follow, slow). Each sentence carries one idea in a simple structure, and no sentence, the first included, makes a claim without a source. Then the procedure people use, where it is used, and what its output is taken to estimate, ending with one concrete published example: the data, what was computed, and how its authors read the estimate (the SS1 draft's lionessR sentences are the model). A first sentence that a reader could not paraphrase is rewritten in the revision pass. Paragraph 2: the realistic condition, what the procedure estimates under it, in words and then as a formula, and what has been observed or derived before, with what each source did and did not do, ending in what has not been derived. Paragraph 3: what this paper does, in the order of the sections. Almost every sentence is a fact with a reference; the rest build the tension and resolve it. The paper's claims are the spec's aims, phrased as questions that can come out either way.

**Methods.** *The estimand and the procedure:* the estimand as a feature of a population, as a functional, in plain words first; then each procedure as a recipe applied to data, with the equations one clause per line and each symbol defined in the sentence that introduces it or in the equation's own label. No table of notation: it is not common practice, and a symbol a reader has to look up in a table was introduced in the wrong place. *What the procedure estimates:* the target under the realistic condition and the bias as a formula, saying when it is zero and what makes it large; where no formula exists, say so. Proofs go to `_supplement.qmd`. *The fix or the diagnostic:* what to change, or what to check. *Data:* the cohort, accession, sizes, and processing. *Software and reproducibility:* the standard paragraph from `parts/`. Past tense, no results.

**Simulation study.** *Design:* the ADEMP sentence, then aims, data-generating mechanisms with the factors varied and fixed and the reason for each, estimands, methods precise enough to reimplement, performance measures, replicates and the Monte Carlo SE they give; the design table through `design_table()`, whose caption defines every study label it uses (S1, S2) and whose reason cells read as fragments a reader can parse, in the paper's words and not the workflow's ("a small effect", never "too small to matter"). *Results:* one subsection per aim, each with its figure or table chunk reading `results/`, never hard-coding factor levels, and prose that states facts in past tense, cites nothing, and states a difference only when it exceeds about three Monte Carlo SEs, otherwise marks it `[TO CONFIRM: ...]{.tc}`. Every figure and table is referenced. Every finding the prose states is shown in a figure or a table, and no cell that supports a finding is dropped from a display: a condition under which a method misbehaves (heavy tails, undefined tests, a cell that would swamp an axis) gets its own row, panel, or table rather than an exclusion.

**Application.** The dataset and comparison, then the one thing the analysis shows, as a claim about a user's conclusion, with the real data placed on the simulation's gradient, in a table whose rows carry the design table's symbols ($\pi$, $\delta$, $s$, $\rho$, $\Delta\rho$) beside the quantity each row reports, every row readable on its own. If the analysis has not been run, the claim stands with a marker and a guarded chunk.

**Discussion.** What was found and what a user should do differently; the novelty table (element, prior literature, this paper) through `novelty_table()`; limitations from the critique table's rows that did not become design factors; future work from the spec's out-of-scope list, item by item.

**Statement on AI use** and **Data and code availability** from `parts/`, the first adapted to the journal's policy as quoted in its profile.

## Provenance

- Every number in the text comes through `prov(x, digits)`, which reads the run label from `results/run_info.rds` (fields `run`, one of `pilot`, `quick`, `production`; `n_rep`; `n_cells`; `date`; `note`; and `n_rep_production`, which `gap_register()` uses for its production column) and renders the number with a visible mark in draft mode. Every analysis script writes that file. A number from a second results file with a different run label takes `prov(x, run = "pilot")`.
- Design levels (a factor's value, a sample size, a nominal level) go through `lvl()`, which formats without a highlight; ranges with their Monte Carlo error go through `range_mcse()`, which reports the largest MCSE once.
- Markers are spans: `[TO CONFIRM: the decision]{.tc}` for any decision a person must make, `[CITE: the claim]{.cite}` for a claim without a usable source, `[FILL: ...]` only in the skeleton. A marker in the YAML (an author line, say) carries its span too, and Quarto renders it in the title block. The banner, the marker table, and the checker count markers in every line of the qmd (front matter and chunks included) and in every included file, so their counts agree; the checker also reports the count in the rendered page.
- `draft_banner()` opens the draft with the log's opening status line, the run label and replicate count, and the marker counts; `gap_table()` closes it with one row per figure or table (register each with `gap_register()` in its chunk) and `marker_table()` lists every marker with its section. All three are apparatus and the only place workflow words may appear.
- `manuscript/drafting-log.md` opens with a one-paragraph status (the paper test in a line, and what was not run), then records, section by section, what was carried from which file, what was written new, the paper test, the bounded literature pass (every source opened and what it said), the citation counts (passage-backed against definitional), every deviation from a Zotero record, and every warning kept with its reason. Reading the supporting passages may be delegated to other agents, each returning the quote, its location, and a verdict on whether it supports the sentence; the drafter spot-checks a sample against the PDFs and says so in the log. The checklist's `verified_by` and `verified_date` columns are filled before submission by whoever verifies each citation against the paper; no drafting step fills them.

## Rules for writing

The rules every stage obeys are in `rules.md`, section 4; the ones below are the manuscript's own and the checker's.

- No digit is typed in the prose: results through `prov()`, design levels through `lvl()`.
- The report is a source of facts, never of sentences; its footnotes, figure guides, and worked examples do not appear in the paper.
- Plain language before the formal statement, in every section opener; keep both.
- Real LaTeX for all mathematics; multi-clause displays with one clause per line, separated by `\\`.
- No em or en dashes; the Oxford comma; no bold lead-ins; "we", never "I".
- Estimand, estimator, statistic, and limit are four different things; "valid", "trustworthy", "correct", and "safe" only with the thing they refer to.
- No workflow vocabulary in the paper: not "harness check", "pilot", "card", "worker", "quick run", "spec", or "the report". Say plainly what was done.
- Methods in past tense with no results; Results with no interpretation and no citations; Discussion with no new results.
- Delete on sight: considerably, dramatically, enormously, exceptionally, extremely, highly, quite, remarkably, substantially, very, actually, basically, clearly, essentially, in fact, indeed, just, kind of, of course, really, simply, sort of, certainly, obviously, undoubtedly, important, interesting, notable, remarkable, considerable, major, minor, substantial. Justify or replace: apparently, arguably, can, conceivably, could, maybe, may, might, perhaps, potentially, possibly, presumably, seemingly, would, commonly, frequently, generally, largely, mostly, often, rarely, typically, usually.
- Every citation that attributes a finding or a claim is written with the PDF open and its supporting passage recorded in the checklist; a citation that only names a method or a dataset is marked `definitional` there.
- Table column widths in proportion to the text in each column (`kable_w()` takes `widths`).
- Format: Quarto, `embed-resources: true`, `toc`, `theme: cosmo`, `fig-cap-location: bottom`, `code-fold: true`, `echo: false`, `warning: false`; the journal's CSL file copied beside the qmd and named in the YAML.

## What the checker covers

Errors: a rendered page older than the qmd; a `[FILL]` left; an unresolved cross-reference or footnote; inline R that did not run; an em or en dash; a hand-typed number in the prose; a cited key missing from the bib, missing from the checklist, not usable, or without a supporting passage or `definitional`; a checklist identifier neither filled nor `none`; a figure or table never referenced; a citation inside Results; first person singular; a bold lead-in; a workflow word in the paper's own text; a marker written without its span; in final mode, any marker or any number not labeled production. Warnings: delete-on-sight and justify words with counts; many "not X, Y" constructions; digits with a percent sign in Methods; the abstract or body over the journal's limits; evaluative words; "statistic" near "estimand"; tables with equal-width columns; unused bib entries. Info: numbers by label, markers by kind, figures, tables, citations, words per section. It cannot judge tension, whether the estimand is a functional, or whether a passage supports its sentence; a person does that, and spot-checks a handful of passages against the PDFs.

## Journals

`journals/README.md` has the summary table, the choosing procedure, and a worksheet that ends in a target and a fallback. Each profile names the CSL file, the abstract headings and word limits, and the AI policy the statement is written to. `journal_profile(slug)` reads the row the checker also uses.

## Revision rounds

After the first draft, each message of comments from the person is a round. For a round: apply every comment; where a comment states a general rule, apply it and propose the rule for this file or `rules.md` in the return message, without adopting it; record the round in the log under a dated "Revision" heading as a table (comment, change, where); run the revision pass (step 4) again when the round changed more than three sentences in any section; render and check; commit the round as one commit. Return the table and the proposed rules. The draft is settled when the person says so; `STATUS.md` then moves to stage 4.
