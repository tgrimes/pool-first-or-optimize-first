# CLAUDE.md

Conventions for any AI assistant working in this repository. They apply on top of your other instructions. If a request conflicts with one of them, say so and ask before going ahead.

## This repository runs a workflow

This is one research project, from an idea to a manuscript and its presentation, run with the instructions in `workflow/`. On any message:

1. Read `STATUS.md`: it names the stage the project is in, the open stop, and the workflow version.
2. Read the stage file it names in `workflow/` (for example `workflow/01-idea-review.md`) and `workflow/rules.md`.
3. Read the stage's log in `log/` if one exists.
4. Do what the stage file says for the user's message. A stage ends at a stop with one deliverable the user reads; update `STATUS.md` when you reach it, and wait.

The user's message starts each stage ("look at idea.md", "the proposal is final", "the pilot passed", "here are my comments on the draft"). No stage starts itself.

## Project structure and the two rules

The repository is an R package plus analysis folders (a research compendium) with the workflow's folders beside them.

```
idea.md                  the one input: the research idea, in any state
proposal.md              stage 1's deliverable: the reviewed and verified proposal
project-spec.md          stage 2's spec: question, design, scope
protocol.md              the ADEMP simulation protocol, written at the design stop of stage 3
STATUS.md                the stage, the open stop, the stage record
workflow/                the instructions, one file per stage, plus rules.md, the journal guide, the changelog
log/                     one log per stage: decisions, what was carried from where, process feedback
templates/               the forms the stages fill (proposal, spec, pilot report, background report, reviews)
tools/                   init.R and other scripts that serve more than one stage
DESCRIPTION, NAMESPACE   package metadata; NAMESPACE is generated by roxygen2
R/                       functions only, with roxygen comments; no top-level side effects
tests/testthat/          unit tests for the functions in R/
pilot/                   stage 2: the pre-registration, the pilot script, its results, decisions, and report (pilot-b/ for a re-pilot)
analysis/                numbered scripts (01_..., 02_...) that call functions in R/
data/raw/                untouched inputs: written once, never modified
data/processed/          derived by scripts in analysis/
results/                 everything analysis/ produces; never edited by hand
manuscript/              stage 3: manuscript.qmd, its helpers and checker, citations.csv, references.bib
background/              stage 4: the background report
review/                  stage 5: the mock reviews and responses, one folder per round
slides/, poster/         stages 6 and 7
renv.lock, renv/, .Rprofile   the project library: renv.lock records every package version, .Rprofile activates it
inst/python/             Python functions (a package named like the R package), their tests, and vendored code
pyproject.toml, uv.lock, .python-version   the Python environment: uv.lock records every package version
```

Two rules matter more than the folder names.

1. **Functions are separate from the scripts that call them.** Functions go in `R/`. Scripts in `pilot/` and `analysis/` call them and do not define them.
2. **Generated files are separate from everything else and never hand-edited.** `results/` and `pilot/results/` are written by scripts. If a result is wrong, fix the script and rerun it. `NAMESPACE` and `man/` are generated by roxygen2 (`devtools::document()`), `renv.lock` by `renv::snapshot()`, and `uv.lock` by uv, so do not edit them either.

## Environment

- The project library is managed by renv. On a fresh clone, open R in the project root and run `renv::restore()`: renv installs itself on first start, then installs every package at the version recorded in `renv.lock`. Install nothing outside the project library, and never install into a user or system library on the project's behalf. For a package project renv keeps the library in its own user directory, outside the repository.
- `DESCRIPTION` declares the dependencies; `renv.lock` records their versions. After adding or removing a dependency in `DESCRIPTION`, run `renv::install()` and then `renv::snapshot()`, and commit `renv.lock` with the change. Updating package versions is a deliberate act: `renv::update()`, then `renv::snapshot()`, with the reason in the commit message.
- renv does not pin R itself. `renv.lock` records the R version used, and the `sessionInfo()` saved with each run records the rest.
- Run scripts and renders from the project root, where `.Rprofile` activates the project library; `manuscript/.Rprofile` does the same when R starts in `manuscript/`.
- Python, when the project uses it, is managed by uv in the same way (the Python section below).

## R

- Follow Google's R Style Guide: BigCamelCase function names, snake_case variables, two-space indentation, `<-` for assignment, lines under 80 characters. Comment assumptions briefly.
- Prefer base R for simulation code. Add a dependency only when it earns its place, and declare it in `DESCRIPTION`.
- Put roxygen comments on every function.
- Write a test for every function that computes something. Known-answer checks and code-identity checks are tests, never content of a deliverable.

## Python

The compendium may carry Python beside R, under the same two rules.

- Functions go in `inst/python/<package>/`, a package named like the R package, with a docstring on every function (Google style) and a pytest test in `inst/python/tests/` for every function that computes something. No top-level side effects, no notebooks.
- The environment is managed by uv as the R library is by renv. `uv sync` on a fresh clone creates `.venv/` with the interpreter pinned in `.python-version` (uv installs it if the machine lacks it) and every package at the version recorded in `uv.lock`. `uv add 'name==version'` adds a dependency to `pyproject.toml` and updates `uv.lock`; commit both. Install nothing outside `.venv/`, and never through Homebrew, pyenv, or conda on the project's behalf.
- Run Python through uv: `uv run pytest` for the tests, `uv run analysis/02_name.py` for a script.
- A script in `analysis/` may be Python when a step cannot be driven from R. It follows the script rules below: numbered, calling functions from the package, a seed, output only to `results/` and `data/processed/`, and a run file `results/<name>_run_info.json` with the fields of `run_info.rds`.
- R reaches Python through reticulate (in `Suggests`), which `.Rprofile` points at `.venv/`. An R wrapper in `R/` stays thin, and its test is skipped when `.venv/` is absent.
- Third-party code that is not a package, such as a method published as scripts, is vendored into `inst/python/vendor/<name>/` with its license file and a `SOURCES.md` that records the repository, the commit, and the date. Vendored files are never edited; any adaptation lives in the glue that imports them. A method published as scripts that read and write files at the top level cannot be imported: re-express it in the glue for the inputs the project needs, and test the glue equal to the unchanged scripts run on the same data and to any outputs the authors ship.

## Scripts

- Start every script with `devtools::load_all()`, not `source()`.
- Build paths with `here::here()`. Never use `setwd()` or absolute paths.
- Every script sets a seed. Simulations give each cell its own seed, derived from the design table.
- Every script writes its run file (`results/run_info.rds` for the simulation script, `results/<name>_run_info.rds` for any other; `pilot/results/run_info.rds` for the pilot) with `run` (`pilot`, `quick`, or `production`), `n_rep`, `n_cells`, `date`, `note`, and `n_rep_production`, and saves `sessionInfo()`.
- Scripts write to `results/`, `pilot/results/`, and `data/processed/`. A download script (by convention `analysis/00_download.R`) may also write to `data/raw/`: it skips any file that already exists, and nothing modifies or overwrites a raw file afterward. Scripts never write into `R/` or `manuscript/`.

## Manuscript, report, slides, poster

- Every number in the text, tables, figures, and captions is computed from files in `results/` at render time, through the helpers in `manuscript/manuscript-helpers.R`. Nothing is typed in by hand. If you need a number, add it to a script that writes it to `results/`, then read it.
- The writing rules are in `workflow/rules.md`, section 4; the checker in `manuscript/check-manuscript.py` enforces what it can.
- Citations are author-date from `manuscript/references.bib`, built from Zotero by `manuscript/build-bib.py`; every cited item is in Zotero with its passage recorded in `manuscript/citations.csv`.

## Simulation

- No simulation runs before `protocol.md` is written, except the pilot's own pre-registered run. Pilot runs to debug code are fine. Changing the design after seeing production results needs a dated entry, with a reason, at the bottom of `protocol.md`.
- Report Monte Carlo standard errors with every simulated rate, bias, and coverage.

## AI conduct in this repository

- Do not fabricate citations. When you cite a paper, say where it can be checked, and say when you are unsure it exists. The user verifies every citation against the paper itself before it enters a deliverable.
- When asked for a derivation, also propose the numerical check (a simulation, or a special case with a known answer) that would catch an error in it.
- Flag scope creep. Compare any new idea with `proposal.md`, `project-spec.md`, and `protocol.md`, and say plainly when a request falls outside them.
- When the user asks why something is wrong, explain first and fix second.

## Directories

The folders in the structure block are the only top-level folders. A re-pilot adds `pilot-b/`, `pilot-c/`, and so on. Do not create any other top-level directory without asking.
